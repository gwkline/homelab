# Work Docker KVM runtime

Docker runs inside a separate guest kernel on the existing node. T3 contains only the pinned Docker client, Compose and Buildx. Work uses a dedicated mTLS authority; personal T3 has no daemon endpoint or certificate mount. The work namespace stays restricted, tokenless, RuntimeDefault seccomp and without any host Docker/containerd socket.

## Boundaries

- QEMU runs as `work-dockervm`, with only its primary group and `kvm`, no login or sudo, no capabilities and NoNewPrivileges. Its AppArmor profile, strict filesystem namespace and closed device policy limit it to KVM, its guest disk/runtime, and explicit **read-only** source exports. No TAP/bridge, PCI passthrough, TCP monitor, VNC, host commands or guest Tailscale identity.
- The guest daemon's client certificate grants **guest root**, not node root. The CA signing key and work client key remain outside the guest. Only the server leaf/key and public CA enter the private NoCloud seed. Generated service credentials are documented in [the inventory](../../docs/secrets-inventory.md), not bridged from unrelated 1Password items.
- SLIRP alone is not an isolation boundary. A dedicated `inet work_docker` nftables table limits API/relay ingress to the **current ready work pod**. A host-only ServiceAccount can only `get` named `work/work-t3code-0` metadata; it cannot list pods, read Secrets or exec. Its source-set refresh is atomic, clears on errors and expires after 15 seconds if the watcher stops.
- VM-UID egress rejects loopback, LAN, tailnet, cluster/service, metadata, special/private ranges and current host addresses. It permits public DNS and HTTP(S). Exceptions are narrowly qualified **reply** flows for the authorized API or marked localhost service relay, not a blanket established-connection escape.
- API port 2376 requires mTLS. Port 2377 is another mTLS endpoint: a two-byte port selector can address only configured guest-service ports. It cannot choose a host or arbitrary host port. Rootless host proxy code forwards only to private QEMU loopback forwards; other host UIDs cannot connect to those forwards. Work's Python client exposes selected ports on **127.0.0.1 only**, so ordinary local database/HTTP clients work. Unlisted ports and UDP are not forwarded.
- Remote bind paths belong to the guest. Exports preserve `/data/repos/<selected-root>` and actual `/home/node/.t3/worktrees/<selected-root>` paths, including `.git` links. Never export `/data`, agent-state, whole `.t3`, userdata, personal roots or authority directories. The installer requires matching host/guest paths and rejects symlinked export ancestry. Guest 9p mounts are `9p2000.L`, `cache=none`, `ro,nodev,nosuid`; host mounts and QEMU's readonly flag also enforce RO. `multidevs=forbid` is not a complete containment boundary; the host UID, filesystem namespace and AppArmor are required. Application dependencies/database writes use guest-local named volumes, never writable work source.

These controls reduce guest-to-host risk; they are not a claim that KVM/QEMU/kernel vulnerabilities cannot escape. Source permissions, symlinks, hardlinks, nested mounts and actual application bind/write requirements need live verification before claiming an application reproduction.

## Filesystem and resource budget

Use an **existing verified separate filesystem**, not a guessed disk letter and never a root fallback. No formatting, root-LVM expansion, original PVC deletion or source cleanup is part of this component. Work data and state remain on their copy-and-switch local claims; originals/claims remain rollback copies and do not free old-root headroom ([migration](../work-t3code/README.md#storage)).

The initial gate is 60 GiB **on the new filesystem**: the maximum 32 GiB guest disk, work reserve, cloud base/cache and margin. It is not the obsolete old-root provisioning floor. Every start checks the mounted UUID, separate device and enforced read-only exports. Units use RequiresMountsFor and ConditionPathIsMountPoint. All guest disks, downloaded images/package archives, seeds and guest/runtime logs belong on that filesystem. Root package/image installation is separately measured and bounded.

The guest starts with 4 vCPUs/8 GiB; host limits are 10 GiB MemoryMax, zero host swap, CPUQuota 400%, TasksMax 128 and bounded disk I/O. Guest disk capacity is 32 GiB. The pressure timer stops the **whole VM** below 25 GiB or on mount/measurement failure and writes a persistent host inhibition marker. QEMU has no automatic restart. An explicit reset requires the verified real launch budget (35 GiB) again. Work's 22/25/20 GiB guards remain unchanged and measure the actual shared SSD through `/data`; these are cooperative watermarks, not PVC quotas.

## Provision from merged, green source

1. Record original work replicas/deployer suspension, pod/image and all old/new PVC UIDs, source Git/auth/environment/SQLite state. Preserve dirty, untracked, ignored, benchmark and worktree files. Budget trusted distro package installation and new image layers separately; never clean user files to make a gate pass.
2. Install distro-security QEMU 8.2, qemu-utils, cloud-image-utils, AppArmor tools and ubuntu-cloudimage-keyring without a full host upgrade or reboot. Keep package archives on the verified new mount. Authorized temporary root helpers are maintenance-only and tokenless; include only necessary capabilities, including **FSETID** when preserving setgid metadata. Remove exact helpers and verify absence afterward.
3. Download Noble's cloud image, SHA256SUMS and SHA256SUMS.gpg to `<mount>/image-cache`. Verify the signature using the installed official ubuntu-cloudimage-keyring and full image SHA-256. The installer repeats these checks before making any guest disk. Resolve and pin Docker's official Noble package version/key hash; do not fabricate downloads or metadata.
4. Generate the work-only mTLS CA/server/client through private files (0700 authority directory, private keys 0600), with serverAuth/IP SAN and clientAuth EKUs. Never put keys/tokens into git, PRs, argv, chat or logs. Store the CA signing key separately from VM files; human-managed credentials belong in 1Password, with pointers rather than values in chat. Do not create an ESO placeholder or rotate unrelated credentials.
5. Supply a private root-owned config to `install.py`: verified `mount`, `uuid`, node `address`/`local_ips`, `node`/`pod_cidr`, actual matching `sources[{host,guest}]`, bounded `ports{guestPort:loopbackBridgePort}`, `cpus`, `memory_mib`, `disk_gib`, `start_gib`, `stop_gib`, unique `instance_id`, official `docker_version`/`docker_key_sha256`, server leaf paths and host-only watch API/CA/token paths. No source/auth identifiers are public inputs. The installer does not download, delete, or modify work sources, and refuses changes while the guest runs.
6. Suspend deployment before merging endpoint/certificate consumers. Apply **only** new RBAC/token, work endpoint ConfigMap and work Docker NetworkPolicy prerequisites from the merged **clusters/home render**: the sibling endpoint's node replacement occurs after composition, not in the standalone base. Create `work-docker-client` by server-side apply through private files, never an empty Secret. Verify actual authority/hash and metadata-only RBAC before copying the token to its host-only path.
7. Install merged code/private units, validate AppArmor/systemd/nft syntax and absence of a conflicting table. Enable/start dedicated network, watcher, proxy, guard timer and VM services. Do not flush global nftables/k3s rules. Confirm the guest has actually booted, installed the pinned daemon and mounted the intended RO sources.
8. Run the current managed deployer with signed immutable images, then restore original replicas/suspension and remove exact maintenance helpers. If its in-cluster Node runtime is unavailable, execute its **original bytes** from a private Mac driver with explicit verified-CA kubectl and a scratch-only work path; do not rewrite redaction markers or debug unrelated runtime failures.

## Required live acceptance

Do not call a client version, plan, HTTP check or unexercised VM recipe a usable application environment. Record real mTLS `docker info`, public pull/run, Dockerfile build; Compose up/down; actual worktree/.git bind reads and source-change visibility; named-volume persistence; and a published HTTP/database port from T3 through the authenticated relay. Verify no-cert/wrong-cert and unauthorized pod/LAN denial, guest-root inability to reach private/metadata/node endpoints or read/chmod personal/auth sources, actual UID/AppArmor/seccomp/capability/device/resource limits, and a pressure fixture that stops/inhibits the whole VM **without filling a disk**. Reset only after checking real headroom; verify the restart and both T3 routes/state/Git behavior. Keep protected-source/audit evidence private.

Application `.env`, cloud-auth and temporary source-mirror paths must be discovered in the actual checkout. Never invent missing configuration or export a home/auth directory to make a Compose command pass. Infrastructure smoke tests and a full employer application reproduction are separate claims; report any unmet gate explicitly.

Rollback: stop the VM and client forwarding; preserve guest disk/volumes, all source and all old/new work claims. Disable only these exact new units/table and restore reviewed workload configuration through git. Do not delete data, widen work privileges, restart the host or touch unrelated services.
